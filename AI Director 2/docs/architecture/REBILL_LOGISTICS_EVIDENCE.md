# Доказательство экономического смысла `rebillLogisticCost`

Дата: 2026-09-04. Статус: **блокировка снята доказательством, а не решением по умолчанию.**

Поле было последним финансовым блокером P&L: пока его направление не установлено,
`net_profit` не мог быть полным результатом (см. `STAGE_9_BLOCKER.md`,
`FINANCIAL_POLICY_GATES.md`).

## 1. Вывод

`rebillLogisticCost` — **удержание с продавца** (расход операционного дня).
Канонический знак: **отрицательный**. В P&L участвует: **да**.

```text
source field          rebillLogisticCost        (нестрицательная величина)
raw value             +76.92                    (знак источника не тронут)
canonical value       -76.92                    (знак назначен политикой, не abs())
kernel                FinancialComponentInput(state=PROVIDED, amount=-76.92)
```

Владелец знака — `packages/finance/marketplace_policy.py`. Ядро политику не импортирует.

## 3. Само доказательство: НДС-база источника

WB на каждой rebill-строке отдаёт разложение операции по НДС. Оно **отрицательное**:

```text
vw    = -rebillLogisticCost / 1.22
vwNds = -(rebillLogisticCost - |vw|)
```

Проверено построчно на всех 20 строках, с точностью до копейки:

| `rebillLogisticCost` | `vw` | `vw × 1.22` | `vwNds` | `|vw| + |vwNds|` |
| --- | --- | --- | --- | --- |
| 7.68 | −6.2950819672131148 | −7.68 | −1.38 | 7.68 |
| 2.76 | −2.2622950819672131 | −2.76 | −0.50 | 2.76 |
| 1.78 | −1.4590163934426230 | −1.78 | −0.32 | 1.78 |
| 2.01 | −1.6475409836065574 | −2.01 | −0.36 | 2.01 |
| 11.02 | −9.0327868852459016 | −11.02 | −1.99 | 11.02 |
| 21.66 | −17.7540983606557377 | −21.66 | −3.91 | 21.66 |

**Нарушений: 0 из 20. Контрпримеров: нет.**

Распределение знака `vw` по всем 40 строкам:

| знак `vw` | строк | какие операции |
| --- | --- | --- |
| отрицательный | 20 | только «Возмещение издержек …» (rebill) |
| положительный | 5 | только «Продажа» |
| ноль / отсутствует | 15 | Доставка, Логистика, Хранение, Обработка товара, лояльность |

Отрицательная база НДС в отчёте о продажах — бухгалтерный признак операции,
**уменьшающей выручку продавца**, то есть удержания. Начисление в пользу продавца
имело бы положительную базу (как «Продажа») либо не имело бы её вовсе (как логистика
и хранение, где `vw = 0`).

## 4. Почему не «выплата продавцу»

Проверенная альтернативная гипотеза: «возмещение» = WB возвращает деньги продавцу.
Данные её отвергают:

1. `forPay = 0` на всех 20 строках — продавцу по этой операции ничего не перечисляется.
2. `retailAmount = 0` — движения товара нет, это не продажа и не возврат продажи.
3. `vw`/`vwNds` отрицательные — операция уменьшает налоговую базу выручки продавца.
4. `quantity = 2` на каждой строке — это счётчик отгруженных единиц, по которым
   пересчитаны фактические издержки, а не возврат по конкретной продаже.
5. Само имя поля — `rebill` — повторное выставление счёта тому, кто его оплачивает,
   то есть продавцу; в названиях операций прямо сказано «возмещение **издержек**».
6. Approved-контракт проекта (`docs/METRICS_PASSPORT.md` §3.6, §3.12) и раньше считал
   `rebill_logistic_cost` расходом, вычитаемым из прибыли; доказательство подтвердило
   эту трактовку, а не изменило её.

Значение «компенсация» в бытовой формулировке WB описывает возмещение **издержек
маркетплейса**, а не доход продавца. Именно поэтому знак брался из роли поля, а не
из буквального прочтения русского слова.

| `packages/finance/kernel.py` | **без изменений** — ветка `REBILL_LOGISTICS` в компонентах уже суммировала PROVIDED-значения |

Знак по-прежнему назначается таблицей политик по роли поля. Отрицательное значение
источника при положительном ожидаемом знаке уходит в `UNRESOLVED` с сохранением
исходной суммы — механизм остался и защищён тестом.

## 6. Как это опровергнуть (критерий фальсификации)

Трактовка неверна, если на реальных данных появится хотя бы один из случаев:

* `rebillLogisticCost > 0` и одновременно `vw > 0` на той же строке;
* `rebillLogisticCost < 0` (тогда политика уже сама отдаёт компонент в `UNRESOLVED`
  с исходным знаком — он не превращается в доход);
* `forPay > 0` на строке возмещения.

Ни одного такого случая в 40 реальных строках нет. Проверка закреплена тестом
`test_rebill_evidence_stays_inspectable_in_the_canonical_record`: `vw` и `vwNds`
сохраняются в канонической записи, поэтому доказательство можно перепроверить
на любом новом выгрузке, не меняя код.

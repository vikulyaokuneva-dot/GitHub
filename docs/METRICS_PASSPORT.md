## 2. Коммерческие метрики (Commerce)

### 2.1. Количество заказов (orders_count)

| Поле | Значение |
|------|----------|
| **Название** | Количество заказов |
| **Где отображается** | Ежедневный отчёт (Commerce KPI), PDF (стр. 2), Email, Dashboard |
| **Первичный источник** | Orders API: `GET /api/v1/supplier/orders` → поле `quantity` |
| **Источник внутри проекта** | `v3/daily_kpi_resolver.py` → функция `resolve_daily_kpi()` |
| **Метод получения** | Напрямую из API (агрегируется по дням) |
| **Формула** | `SUM(order.quantity) WHERE date = target_date` |
| **Возможность восстановления** | YES — fallback: Supplier Goods Daily → Sales API → Realization API → totals hint |
| **Надёжность** | A — первичный источник WB (Orders API) |
| **Проверка корректности** | Сверка с кабинетом WB; подтверждение через `orders_count_confirmed` флаг |
| **ИИ при анализе** | YES — используется в Health Score (вес 2.0), Decision Engine (пороги 10/3/1), AI Director (задачи мониторинга) |

> **Целевой контур (AI Director 2, STAGE 20.22):** Orders/Sales API WB
> возвращает окно `lastChangeDate >= dateFrom`, в которое попадают строки и
> соседних дней (поздние изменения старых заказов). Нормализатор
> (`packages/data/normalization.py`) относит строку к дню аудита только если
> её собственный `date` совпадает с этим днём — это прямое применение формулы
> `WHERE date = target_date`, а не её изменение. Сырое окно сохраняется в
> RawObject без правок; неатрибутируемые строки не дописываются ни к одному
> дню. Тот же принцип действует для `buyouts_count` (Sales API). Тесты:
> `AI Director 2/tests/unit/test_statistics_window_day_attribution.py`.

#### Восстановление дневной истории Commerce KPI

`orders_amount` и `buyouts_amount` в историческом сравнении сохраняются в
`history/history_index.json`. Если в истории есть подтверждённое количество,
но денежное значение отсутствует или ошибочно равно нулю, `report_v2`
восстанавливает сумму только из сохранённого `wb_api_core/*/snapshot.json` с
той же `operational_date`. Snapshot другой операционной даты не используется.
Восстановленная запись получает признак
`history_recovered_from = wb_api_core_snapshot`.

При повторной загрузке одной `operational_date` применяется правило
no-downgrade: более полный сохранённый snapshot имеет приоритет над новым
неполным ответом API. Замена выполняется отдельно для Commerce, Funnel,
Finance и live-блоков; восстановленные блоки получают
`stale_reason = same_operational_snapshot_preserved`.

Перед публикацией `report_v2` проверяется подтверждение текущего операционного
дня. Достаточно доступного Commerce/Funnel/live источника с фактическими
значениями, включая подтверждённые нули. Если после fallback текущий день не
подтверждён, PDF не публикуется: отсутствие данных не подменяется нулями и не
заменяет ранее сохранённый отчёт.

### 3.12.1. Целевой контур (AI Director 2): политика знаков удержаний WB

Владелец правила — `packages/finance/marketplace_policy.py` (версия
`marketplace-sign-policy-v1`). Нормализация (`packages/data`) сохраняет поле
ровно с тем знаком, который прислал WB; экономический смысл присваивает только
эта таблица; ядро (`packages/finance/kernel.py`) складывает уже знаковые
компоненты и не знает ни про WB, ни про знаки.

Доказательная база: 40 реальных строк
`/api/finance/v1/sales-reports/detailed` из двух отчётов с устойчивыми `rrdId`.
Во всех строках денежные поля удержаний **ненулевого знака не имеют**: WB
присылает величину списания положительным числом, а тип строки задаёт
`sellerOperName` («Логистика», «Доставка», «Хранение», «Обработка товара»,
«Возмещение издержек …»). Отрицательное значение поля для этого источника —
аномалия, а не «минусовая комиссия».

| Компонент | Поле WB | Знак в источнике | Канонический знак | Участие в P&L | Статус |
|-----------|---------|------------------|-------------------|---------------|--------|
| `realized_revenue` | `retailAmount` | ≥ 0 | ≥ 0 | да | CONFIRMED |
| `marketplace_commission` | `ppvzSalesCommission` | ≥ 0 (напр. 232.46) | ≤ 0 (`−raw`) | да | CONFIRMED |
| `logistics` | `deliveryService` / `deliveryRub` | ≥ 0 (31.2, 44.2, 312.98) | ≤ 0 (`−raw`) | да | CONFIRMED |
| `storage` | `paidStorage` / `storageFee` | ≥ 0 (5.89, 6.29) | ≤ 0 (`−raw`) | да | CONFIRMED |
| `acceptance` | `paidAcceptance` | ≥ 0 (10) | ≤ 0 (`−raw`) | да | CONFIRMED |
| `acquiring` | `acquiringFee` | ≥ 0 (33.36, 24.2) | ≤ 0 (`−raw`) | да | CONFIRMED |
| `penalties` | `penalty` / `penaltyAmount` | ≥ 0 (в выборке 0) | ≤ 0 (`−raw`) | да | CONFIRMED |
| `other_marketplace_deductions` | `deduction` | ≥ 0 (в выборке 0) | ≤ 0 (`−raw`) | да | CONFIRMED |
| `rebill_logistics` | `rebillLogisticCost` | ≥ 0 (76.92, 46.91) | ≤ 0 (`−raw`) | да | CONFIRMED |
| — | `cashbackAmount`, `spp`, `kvw`, `kvwBase`, `vw`, `vwNds`, `loyaltyDiscount`, `sellerPromo*`, `installmentCofinancingAmount`, `supRatingUp` | ≥ 0 | — | нет | нет утверждённой политики |

Правила применения (все покрыты тестами):

1. `raw > 0` → компонент `PROVIDED` с суммой `−raw`;
2. `raw = 0` → компонент `PROVIDED` с нулём: это ноль, заявленный источником, а
   не подставленный;
3. `raw < 0` → компонент `UNRESOLVED` с **сохранённым исходным значением**;
   знак не «чинится», `abs()` в этом пути запрещён статическим тестом;
4. `rebillLogisticCost` подтверждён как удержание продавца: на всех 20 реальных
   строках источника `vw = −rebillLogisticCost / 1.22`, а `vwNds` — отрицательный
   НДС той же суммы, то есть WB бухгалтерски регистрирует операцию как
   **уменьшение выручки продавца**. Доказательство и критерий опровержения:
   `AI Director 2/docs/architecture/REBILL_LOGISTICS_EVIDENCE.md`. Для компонента
   с неподтверждённым знаком сохраняется правило: нулевая сумма не создаётся —
   ноль не может исказить итог и не должен навечно оставлять период частичным;
5. `UNRESOLVED` с материальной суммой делает период `PARTIAL`, а `net_profit`
   остаётся `None`: «данные есть, но их смысл не подтверждён» — отдельное
   состояние, а не ноль и не нехватка данных;
6. денежные поля без политики не отбрасываются молча: адаптер выдаёт
   диагностику «excluded, not zeroed» с суммой;
7. поле `quantity` с отрицательным значением больше не разворачивается через
   `abs()`: выручные представления по такой строке не строятся, факт уходит в
   диагностику;
8. строка, у которой `retailAmount` равен нулю по самому источнику, не даёт
   диагностику «исключено из выручки»: исключать нечего, и отчёт не вправе
   утверждать обратное.

Формула целевого ядра (то же самое, что исполняет `calculate_financial_result`):

```text
net_profit = realized_revenue
           + marketplace_commission + logistics + storage + acceptance
           + acquiring + penalties + other_marketplace_deductions
            + rebill_logistics
           + advertising + cogs + tax          (все слагаемые уже знаковые)
```

Удержаниями `cashbackAmount` и аналогичными полями без утверждённой политики итог
не уменьшается: они в формулу не входят и показаны отдельной диагностикой
(«excluded, not zeroed»).

### 10.7. Каскадные зависимости (цепочки пересчёта)

Если меняется одна базовая метрика — автоматически пересчитываются все dependent.

```
Цепочка 1: Изменение gross_revenue
  gross_revenue
    ├─► profit          (gross_revenue - commission - logistics - storage - penalties - tax - cogs)
    │     ├─► margin    (profit / gross_revenue)
    │     ├─► ABC Class (Pareto по profit)
    │     ├─► Health Score (компонента profit)
    │     ├─► Opportunity Score (margin × buyout_rate × ABC × health)
    │     └─► Decision Engine → action → AI Director → strategy
    ├─► tax             (gross_revenue × tax_rate)
    ├─► seller_payout   (gross_revenue - commission - logistics - ...)
    └─► avg_check       (gross_revenue / buyouts_count)

Цепочка 2: Изменение clicks (реклама)
  clicks
    ├─► CTR             (clicks / impressions)
    ├─► CPC             (spend / clicks)
    └─► CPM             (spend × 1000 / impressions)  — NO, CPM = spend*1000/impressions, не зависит от clicks
        (CPM зависит только от impressions + spend)

Цепочка 3: Изменение impressions (реклама)
  impressions
    ├─► CTR             (clicks / impressions)
    └─► CPM             (spend × 1000 / impressions)

Цепочка 4: Изменение ads_spend (реклама)
  ads_spend
    ├─► CPC             (spend / clicks)
    ├─► CPM             (spend × 1000 / impressions)
    ├─► CPO             (spend / ad_orders)
    ├─► DRR             (spend / revenue_attr)
    ├─► ROAS            (revenue_attr / spend)
    ├─► ROMI            ((revenue_attr - spend) / spend)
    ├─► Profit_from_Ads (revenue_attr × margin - spend)
    └─► profit          (gross_revenue - ... - cogs - ads_spend?)  — нет, ads_swrite НЕ входит в profit напрямую
        (ads_spend влияет только на рекламные метрики, не на P&L)

Цепочка 5: Изменение stock_qty (остатки)
  stock_qty
    ├─► Days of Cover   (stock_qty / avg_daily_sales)
    │     └─► Risk of OOS (days_of_cover < threshold)
    ├─► ABC Class       (косвенно, через profit)
    └─► Health Score    (компонента stock)

Цепочка 6: Изменение orders_count (заказы)
  orders_count
    ├─► Buyout Rate     (buyouts_count / orders_count)
    │     ├─► Health Score
    │     └─► Opportunity Score
    ├─► CPO             (spend / ad_orders)
    └─► Decision Engine

Цепочка 7: Изменение buyouts_count (выкупы)
  buyouts_count
    ├─► Buyout Rate     (buyouts_count / orders_count)
    ├─► Avg Check       (buyouts_amount / buyouts_count)
    └─► Health Score    (компонента buyout_rate)
```

## 11. Реестр проблемных мест

### 11.1. Отсутствующие метрики

| Метрика | Статус | Описание |
|---------|--------|----------|
| **Трафик из кабинета (organic views)** | Нет прямого источника | Показы берутся из Advertising API или Cabinet Funnel, но нет отдельного органического трафика |
| **Стоимость возвратов** | Приблизительная | Возвраты учитываются как отрицательные продажи, но нет данных о себестоимости возвратов |
| **Прибыль по SKU из API** | Нет | WB не предоставляет прибыль по SKU — всегда рассчитывается клиентски |
| **Stock relocation plan** | Stub | `stock_relocation.py` — заглушка, не реализована |

### 11.2. Потенциально проблемные метрики

| Метрика | Проблема | Решение |
|---------|----------|---------|
| **cost_price (sebestoimost)** | Зависит от локального `cogs.json`, может устареть | Регулярное обновление файла; валидация через health_score |
| **profit_from_ads** | Пропорциональная атрибуция может неточно распределять прибыль | Использование query-level attribution при наличии Search API |
| **localization_share** | Может быть неточным при неполных данных о географии | Проверка `confidence` поля; использование `analysis_mode` |
| **Growth Simulation** | Линейная экстраполяция не учитывает немонотонность спроса | Ограниченный прогноз: только 10/20/30% |
| **KTR (при отсутствии territorial данных)** | Не рассчитывается без данных о распределении спроса/остатков | `insufficient_data` статус; подавление рекомендаций |

### 11.3. Метрики, вычисляемые через несколько API

| Метрика | Источники |
|---------|-----------|
| **net_profit** | Finance API + Ads API + COGS (локальный файл) |
| **CTR** | Advertising API (clicks + impressions) или Cabinet Funnel (views + clicks) |
| **buyout_rate** | Orders API (orders) + Sales API (buyouts) |
| **cart_rate** | Cabinet Funnel API (add_to_cart + views) или Advertising API |
| **ROMI** | Ads API (spend) + Finance API (revenue) + COGS |
| **opportunity_score** | Finance (profit/margin) + Orders/Sales (buyout_rate) + ABC + Health |
| **health_score** | Orders + Sales + Finance + Funnel + Ads (6 источников) |
| **territorial metrics** | Orders/Sales (demand geo) + Stocks (stock geo) + Finance (price) |

### 11.4. Места приближённых расчётов

| Расчёт | Приближение | Точная альтернатива |
|--------|-------------|---------------------|
| revenue_from_ads | `revenue × min(1, attributed_orders / total_orders)` | Данные атрибуции WB (недоступны) |
| query_revenue | `total_revenue × min(1, query_orders / total_orders)` | Данные атрибуции WB (недоступны) |
| growth_simulation | Линейная экстраполяция traffic × multiplier | A/B тестирование (недоступно) |
| logistics (при отсутствии Finance API) | KTR коэффициенты из `warehouse_logistics_coefficients.json` | Данные Finance API |
| stock_qty | `max(quantityFull, quantity, 0)`; для нового WB Warehouses API используется `quantity`, а транзитные поля не прибавляются | Текущий складской срез WB; отрицательные значения не допускаются |
| IRP penalty | Табличный KRP × price × orders | Точный расчёт WB (недоступен) |

### B.1. Метрики и показатели

| Термин | Определение | Формула / Источник |
|--------|-------------|---------------------|
| **CTR** | Click-Through Rate — кликабельность рекламы | `clicks / impressions × 100` |
| **CPC** | Cost Per Click — стоимость одного клика | `ads_spend / clicks` |
| **CPM** | Cost Per Mille — стоимость 1000 показов | `ads_spend × 1000 / impressions` |
| **CPO** | Cost Per Order — стоимость привлечения одного заказа | `ads_spend / ad_orders` |
| **DRR** | Доля Расходов на Рекламу — процент рекламных расходов от выручки | `ads_spend / revenue_attr` (только если `revenue_attr > 0`) |
| **ROAS** | Return on Ad Spend — возврат на рекламные расходы | `revenue_attr / ads_spend` |
| **ROMI** | Return on Marketing Investment — возврат на инвестиции в маркетинг | `(revenue_attr - ads_spend) / ads_spend` |
| **CR Cart** | Конверсия в корзину (View-to-Cart) | `add_to_cart / views × 100` |
| **CR Order** | Конверсия в заказ (Cart-to-Order) | `orders / add_to_cart × 100` |
| **Buyout Rate** | Конверсия из заказа в выкуп (Order-to-Buyout) | `buyouts_count / orders_count × 100` |
| **ABC** | Метод Парето-классификации SKU по выручке/прибыли | A (до 80% кумулятивно), B (80-95%), C (95-100%) |
| **P&L** | Profit and Loss — отчёт о прибылях и убытках | Формируется построчно из finance API |
| **COGS** | Cost of Goods Sold — себестоимость проданных товаров | Из файла `cogs.json` или legacy-карты `calc_cogs_for_rows()` |
| **Margin** | Маржинальность | `profit / gross_revenue` (доля 0-1) |
| **Avg Check** | Средний чек | `buyouts_amount / buyouts_count` |
| **Days of Cover** | Дни покрытия запасов | `stock_units / avg_daily_sales` |
| **Risk of OOS** | Риск отсутствия товара на складе | `true` если `days_of_cover < (lead_days + safety_days)` |
| **Turnover WB** | Оборот как в WB (по retail_price) | `SUM(retail_price)` по операциям «Продажа» |
| **Days of Cover Avg** | Средние дни покрытия за период | Агрегация по d7 snapshots |

### B.3.1. Цены и платформенные скидки по SKU

| Метрика | Каноническое определение |
|---|---|
| `seller_base_price` | `price` из `GET /api/v2/list/goods/filter`; денежное значение без деления на 100 |
| `seller_price` | `discountedPrice` из `GET /api/v2/list/goods/filter`; каноническая «Цена продавца» в отчёте |
| `seller_discount_percent` | `discount` из `GET /api/v2/list/goods/filter`; скидка продавца |
| `seller_discounted_price` | `discountedPrice` из `GET /api/v2/list/goods/filter`; цена после скидки продавца |
| `club_discounted_price` | `clubDiscountedPrice` из `GET /api/v2/list/goods/filter`; отдельная клубная цена |
| `buyer_price_before_wallet` | `convertedPrice / 100` из FBS-заказа; цена покупателя без скидки WB Кошелька |
| `buyer_final_price` | `convertedFinalPrice / 100` из FBS-заказа; итоговая сумма к оплате |
| `buyer_final_price` fallback | `buyout_sum / buyout_count` по SKU и операционному дню из `sales_funnel_api`; только при явном наличии обоих полей. Источник маркируется `sales_funnel_fallback` |
| `platform_discount_percent` | `(seller_discounted_price_at_order - buyer_price_before_wallet) / seller_discounted_price_at_order × 100`; только при снимке не позднее заказа |
| `wallet_discount_percent` | `(buyer_price_before_wallet - buyer_final_price) / buyer_price_before_wallet × 100`; только при наличии знаменателя |
| `platform_discount_change_day` | средняя платформенная скидка WB за бизнес-день минус средняя за предыдущий доступный бизнес-день |
| `profit_per_unit` | `SKU profit / buyouts`; при `buyouts = 0` значение отсутствует |
| `margin_percent` | `SKU profit / SKU revenue × 100`; при отсутствии выручки значение отсутствует |

Правила качества:

- Все денежные расчёты выполняются через `Decimal`, значения в БД хранятся как `NUMERIC`.
- `captured_at` хранится в UTC; бизнес-день определяется в `Europe/Moscow`.
- Старый заказ связывается только со снимком `captured_at <= order_created_at`. Текущая цена не подставляется задним числом.
- FBS `convertedPrice` / `convertedFinalPrice` имеют приоритет над fallback из воронки.
- Чистая прибыль и маржа SKU не рассчитываются без комиссии, логистики, эквайринга, хранения, удержаний и налога. В этом состоянии показывается предварительный доход до расходов WB.
- Дневная конверсия заказ → выкуп не рассчитывается без когортной связи заказов с выкупами.
- `нет данных` не заменяется на `0`.
- Основное название — «Платформенная скидка WB». `ppvz_spp_prc` является СПП-компонентом финансового отчёта и не переименовывает всю платформенную скидку в СПП.
- Расхождение с финансовым компонентом до `0,50` процентного пункта считается согласованным.
- Автоматическое изменение цен запрещено; резерв повышения цены является только рекомендацией с доказательством и уровнем уверенности.

#### B.7.4. Обработка ошибок и fallback

| Ситуация | Поведение системы |
|----------|-------------------|
| API вернул 429 (rate limit) | Retry с exponential backoff; при исчерпании — fallback в cache |
| Finance API пуст за целевую дату | Лаг до 3 дней: перебор дат `target_date - 1`, `- 2`, `- 3` |
| Finance API вернул 429 | Fallback на legacy API (`reportDetailByPeriod`), затем cache |
| Cabinet commerce вернул 429 | Fallback на fresh cache (6ч), затем stale cache (72ч) |
| Stocks API вернул 429 | Fallback на `latest_successful.json` cache с флагом `stale: true` |
| COGS-файл не найден | `cogs_status = "file_not_found"`, profit считается без себестоимости, warning |
| COGS-файл найден, но SKU не совпадают | `cogs_status = "partial_match"`, warning с list unmatched SKU |
| Finance строки не содержат nmId | SKU P&L не строится, `sku_financials = {}` |
| Воронка показывает 0 buyouts, но sales_api > 0 | Override: buyouts берутся из sales_api (warning: `buyouts_override_from_sales_api`) |

#### B.7.9. Критические правила кода

| Правило | Описание | Код |

# Анализ связей между файлами проекта "ИИ Директор ВБ"

## Два режима работы

### Режим 1: Подключение кабинета ВБ по API ключу (daily)
- Вход: WB API токен из ENV
- Выход: ежедневный KPI-отчёт

### Режим 2: Аудит по приложенным отчётам (audit)
- Вход: Excel-файлы отчётов (xlsx)
- Выход: PDF/MD аудит-отчёт

---

```
                        ┌─────────────────────────────────────┐
                        │            run.py (entry)           │
                        │  --mode daily | audit | audit_ozon  │
                        └────────────┬────────────┬───────────┘
                                     │            │

              ▼                                                          ▼
┌──────────────────────────┐                              ┌────────────────────────────┐

```

## Режим 1: API подключение (Daily Pipeline)

### Точка входа
- `v3/entry.py:1033` → `_run_daily_for_seller()` → вызывает `v3/pipeline/daily_pipeline_runner.py`

### 4 стадии пайплайна
```
daily_input_stage → daily_metrics_stage → daily_ai_stage → daily_output_stage
```

### Ключевые файлы

| Файл | Роль |
|------|------|
| `v3/pipeline/daily_pipeline_runner.py` | Оркестратор 4 стадий |
| `v3/pipeline/daily_input_stage.py` | Сбор данных: API + локальные файлы |
| `v3/pipeline/daily_metrics_stage.py` | Вычисление KPI, метрик, ядро финансов |
| `v3/pipeline/daily_ai_stage.py` | AI-рекомендации, ABC-анализ, решения |
| `v3/pipeline/daily_output_stage.py` | Формирование отчёта, PDF, email |

### Источники данных (в daily_input_stage)
```
token есть? ──► WBApiClient ──► api_realization, api_sales, api_orders, api_stocks
                    │
                    ▼
              local fallback (если API пусто)
                    │
                    ▼
              load_local_reports(seller_input_dir)
```

### API-клиенты
| Файл | Назначение |
|------|-----------|
| `v3/api/wb_client.py` | Новый API-клиент для realization/finance |
| `v3/wb_client.py` | Legacy-клиент для ads + вспомогательные методы |
| `wb_api_core/token_resolver.py` | Разрешение API-токена из ENV |
| `v3/ingestion/api_realization_loader.py` | Загрузка реализации |
| `v3/ingestion/api_orders_loader.py` | Загрузка заказов |
| `v3/ingestion/api_sales_loader.py` | Загрузка продаж |
| `v3/ingestion/api_stocks_loader.py` | Загрузка остатков |

### Конфигурация
| Файл | Назначение |
|------|-----------|
| `v3/config.py` | Загрузка config.yaml/json продавца |
| `cabinets/<seller>/config.yaml` | Конфиг конкретного кабинета |
| `shared/config/seller_config.py` | Shared-утилита загрузки конфига |

### Общие модули (используются обоими режимами)
| Файл | Назначение |
|------|-----------|
| `v3/raw/models.py` | `RawIngestionBundle` — единая модель сырых данных |
| `v3/normalization.py` | Нормализация данных из разных источников |
| `v3/metrics.py` | Расчёт метрик (финансовых, SKU) |
| `v3/metrics/cabinet_funnel_builder.py` | Воронка продаж |
| `v3/metrics/sku_daily_dynamics_builder.py` | Дневная динамика SKU |
| `src/metrics.py` | Метрики ads/funnel/financial (used by audit) |
| `src/pdf_report.py` | Генерация PDF из markdown |
| `src/mailer_yandex.py` | Отправка email |
| `shared/logistics_reference.py` | Справочник логистики |
| `shared/wb_logistics_regions.py` | Регионы логистики WB |

## v3 vs audit: различия в обработке данных

### API mode (daily)
1. **Вход**: API-вызовы к WB + fallback на локальные xlsx
2. **Нормализация**: `v3/normalization.py` → `RawIngestionBundle`
3. **Метрики**: `v3/metrics.py` (собственная реализация)
4. **Ядро финансов**: `v3/metrics.py` → `run_financial_kernel()`
5. **AI**: ABC-анализ, решение, память решений
6. **Выход**: PDF отчёт + email + JSON артефакты

### Audit mode (file-based)
1. **Вход**: Excel-файлы из `cabinets/<seller>/input/`
2. **Парсинг**: `audit/audit_loader.py` (scan + parse functions)
3. **Метрики**: `src/metrics.py` ( shared реализация)
4. **Факты**: `audit/audit_facts_builder.py` (уникальная логика)
5. **Выход**: MD + PDF + JSON facts + actions

### Ключевое различие
- API mode имеет **собственный** `v3/metrics.py` с ядром финансов (kernel)
- Audit mode использует **shared** `src/metrics.py`
- API mode имеет 4-стадийный пайплайн с AI-анализом
- Audit mode — линейный пайплайн: load → facts → report → pdf

## Резюме

1. **Два режима** разделены на `v3/` (API daily) и `audit/` (file-based)
2. **Общие модули**: `src/metrics.py`, `src/pdf_report.py`, `src/mailer_yandex.py`, `shared/logistics_reference.py`
3. **Ключевое различие**: API mode использует `v3/metrics.py` с financial kernel, audit использует `src/metrics.py`
4. **Точка входа**: `run.py` — единый entry с mode switching
5. **Конфигурация**: `cabinets/<seller>/config.yaml` — общая для обоих режимов
6. **Audit mode** зависит от `audit_facts_builder.py` (1400+ строк) — самая большая единица в audit
7. **API mode**依赖于`daily_input_stage.py` (773 строки) — самый большой файл в API pipeline
